# v0.1.0 — first release

First tagged release of k8s-playbook: a catalog of 19 Kubernetes deployment anti-patterns
and a detection harness, usable as a GitHub Action.

## Use it

```yaml
- uses: kyhsa93/k8s-playbook@v0.1.0
  with:
    path: rendered/            # file, directory, or several separated by spaces
    fail-on-findings: 'true'   # 'false' to report without blocking the build
```

Feed it rendered output (`kustomize build` / `helm template`), not templates. Exit code 0 =
everything applicable passed, 1 = findings, 2 = could not run (bad path, no manifests).
A `findings` output (`'true'`/`'false'`) is available to later steps.

## What is in this release

All 19 catalog items ([docs/catalog.md](../catalog.md)) are implemented and
genericity-validated against real tooling (Kustomize, Helm, and live Argo CD / Flux / Kargo
controllers), not only against schemas.

| Category | Items | Harness |
|---|---|---|
| Workload definition | 1-4 | `harness/check_workload.py` |
| Availability / HA | 5-6 | `harness/check_workload.py` |
| Configuration management | 7-8 | `harness/check_config_mgmt.py` |
| Secrets | 9-10 | `harness/check_secrets.py` |
| Deployment / Sync (GitOps) | 11-13 | `harness/check_gitops_state.py` |
| Namespace / Tenancy | 14-15 | `harness/check_namespace_tenancy.py` |
| Networking | 16-17 | `harness/check_networking.py` |
| Autoscaling / Capacity | 18-19 | `harness/check_autoscaling.py` |

`harness/check_all.py` is the aggregate entrypoint the Action runs. It reports `n/a` for a
check whose subject is absent from the input rather than a false `PASS`.

## Known limits

- Catalog items 7-8 (config management) and 11-13 (GitOps state) compare several
  environment renders or read GitOps controller objects, so the Action does not evaluate
  them from a single manifest set; `check_all.py` lists them as not evaluated on every run.
  Run `check_config_mgmt.py` / `check_gitops_state.py` directly for those.
- `apps` (item 13) has a documented root-exclusion caveat for Argo CD and Flux; see the
  README.

## Verification

`scripts/verify-all.sh` (what CI runs on every push/PR to `main`) passes, and the Action
wrapper itself runs against the good/bad fixtures in CI.
